# F17: fnx init cd github — GitHub Actions CI/CD

**Status:** 📋 Planned  
**PRD Section:** Developer experience, continuous deployment  
**Depends on:** F17 (fnx init)

## Problem

After scaffolding a function app with `fnx init`, developers who want to set up continuous deployment to Azure must manually create GitHub Actions workflows. There's no guided experience for generating a production-ready CI/CD pipeline tailored to the function app's runtime and deployment target.

## Scope

### In Scope

- `fnx init cd github` command that generates GitHub Actions workflow for an existing function app
- Supports path argument: `fnx init cd github ./my-func-app` or `--path` flag
- Auto-detects runtime from `app-config.yaml` or project files
- Supports two deployment modes:
  - **Zip deploy** (default) — Build artifacts and deploy via [`Azure/functions-action`](https://github.com/Azure/functions-action)
  - **Container deploy** — Build Docker image and deploy to Azure Container Apps or Functions
- Generates `.github/workflows/deploy.yml` with:
  - Build step appropriate for runtime
  - Test step (if test script exists)
  - Deploy step with Azure credentials
- Includes guidance for setting up Azure credentials (OIDC or service principal)
- **Auto-invokes `fnx init docker`** when container mode selected and no Dockerfile exists
- Clear error messages when run outside a function app directory

### Out of Scope (Future Work)

| Scenario | Why Out of Scope | Future Feature |
| -------- | ---------------- | -------------- |
| **Multi-environment pipelines** | Requires environment strategy | `--environments staging,prod` |
| **Approval gates** | Requires GitHub Environments setup | Manual workflow edit |
| **Self-hosted runners** | Org-specific configuration | `--runner self-hosted` |
| **Matrix builds** | Multiple runtime versions complex | `--matrix` flag |
| **Reusable workflows** | Org-wide workflow standards | Template library |
| **PR validation workflows** | Separate from deploy workflow | `fnx init cd github --pr` |

## Design

### CLI Signature

```bash
# Generate GitHub Actions workflow (zip deploy)
fnx init cd github

# Specify function app path
fnx init cd github ./my-func-app
fnx init cd github --path ./my-func-app

# Container deployment mode
fnx init cd github --container

# Specify Azure resource names
fnx init cd github --app-name my-func-app --resource-group my-rg

# Specify branch trigger
fnx init cd github --branch main

# Non-interactive mode
fnx init cd github --yes
```

### Flags

| Flag | Short | Description | Default |
| ---- | ----- | ----------- | ------- |
| `[path]` | | Positional arg: path to function app directory | `.` (current dir) |
| `--path` | `-p` | Path to function app directory | `.` (current dir) |
| `--container` | | Use container deployment instead of zip deploy | false |
| `--app-name` | | Azure Function App name | (prompt) |
| `--resource-group` | `-g` | Azure resource group | (prompt) |
| `--branch` | `-b` | Branch to trigger deployment | `main` |
| `--output` | `-o` | Output path for workflow file | `.github/workflows/deploy.yml` |
| `--yes` | `-y` | Skip confirmation prompts | false |
| `--verbose` | `-v` | Show detailed output | false |

### Runtime Detection

Same as `fnx init docker` — detects runtime from:

1. `app-config.yaml` → `runtime.name` and `runtime.version`
2. `host.json` → infer from `extensionBundle` or worker runtime
3. Project files → `requirements.txt`, `package.json`, `*.csproj`, `pom.xml`

### Generated Workflow Examples

#### Python (Zip Deploy)

```yaml
# GitHub Actions workflow for Azure Functions
# Generated by fnx init cd github

name: Deploy to Azure Functions

on:
  push:
    branches:
      - main
  workflow_dispatch:

env:
  AZURE_FUNCTIONAPP_NAME: 'my-func-app'
  AZURE_FUNCTIONAPP_PACKAGE_PATH: '.'
  PYTHON_VERSION: '3.11'

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: ${{ env.PYTHON_VERSION }}

      - name: Install dependencies
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements.txt

      - name: Run tests
        run: |
          pip install pytest
          pytest tests/ --tb=short
        continue-on-error: true

      - name: Login to Azure
        uses: azure/login@v2
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}

      - name: Deploy to Azure Functions
        uses: Azure/functions-action@v1
        with:
          app-name: ${{ env.AZURE_FUNCTIONAPP_NAME }}
          package: ${{ env.AZURE_FUNCTIONAPP_PACKAGE_PATH }}
          scm-do-build-during-deployment: true
          enable-oryx-build: true
```

#### Container Deploy (Any Runtime)

When `--container` flag is used:

```yaml
# GitHub Actions workflow for Azure Functions (Container)
# Generated by fnx init cd github --container

name: Deploy to Azure Functions (Container)

on:
  push:
    branches:
      - main
  workflow_dispatch:

env:
  AZURE_FUNCTIONAPP_NAME: 'my-func-app'
  REGISTRY: 'ghcr.io'
  IMAGE_NAME: ${{ github.repository }}

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Log in to Container Registry
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Extract metadata
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=sha,prefix=
            type=raw,value=latest

      - name: Build and push
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}

      - name: Login to Azure
        uses: azure/login@v2
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}

      - name: Deploy to Azure Functions
        run: |
          az functionapp config container set \
            --name ${{ env.AZURE_FUNCTIONAPP_NAME }} \
            --resource-group ${{ secrets.AZURE_RESOURCE_GROUP }} \
            --image ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }}
```

### Azure Credential Setup Guidance

The generated workflow uses **OIDC (OpenID Connect)** authentication by default, which is more secure than storing service principal secrets.

**Documentation:** [Authenticate to Azure from GitHub Actions by OpenID Connect](https://learn.microsoft.com/azure/developer/github/connect-from-azure-openid-connect)

The CLI displays a link to this documentation after generating the workflow.

### Error Handling

| Stage | Error | Message |
| ----- | ----- | ------- |
| Directory check | Not a function app | `✗ Not a function app directory at '<path>'. Run 'fnx init' first.` |
| Runtime detection | Cannot detect runtime | `✗ Cannot detect runtime. Ensure app-config.yaml or project files exist.` |
| File write | Workflow exists | `✗ Workflow already exists at .github/workflows/deploy.yml. Use --force to overwrite.` |

### Container Mode Behavior

When `--container` is specified and no Dockerfile exists, the command automatically invokes `fnx init docker`:

```text
? Deployment method: Container deploy

No Dockerfile found. Generating one...
  ✓ Created ./Dockerfile
  ✓ Created ./.dockerignore

Creating workflow...
  ✓ Created .github/workflows/deploy.yml
```

This seamless flow eliminates the need for users to run separate commands.
